## はじめに

こんにちは、エンジニア2年目のはなまるです！

ロックについて調べ始めると、すぐにこんな壁にぶち当たりませんか？

「排他ロックと悲観的ロックって何が違うの？」
「レコードロックとアプリケーションロックって同じ並びで語っていいやつ？」

言葉が多すぎて脳内がぐちゃぐちゃ状態になりますよね:crying_cat_face:

恥ずかしながら、私も雰囲気で言葉を使用していたところがあります...

ということで！「ロックの用語は『3つの軸』で整理すると一発でわかるよ」ということをお話していきます！

今回扱うロックは次のとおりです。
- DBロック
- レコードロック
- 共有ロック
- 排他ロック
- 悲観的ロック
- 楽観的ロック
- デッドロック
- アプリケーションロック

---

## ロック用語が混乱する理由は「軸」が混ざっているから

まず、なぜ用語が混乱するのか。
それは「どこを」「どうやって」「いつ」という全く別の次元の話が、同じ「〇〇ロック」という名前で並んでいるからです。

「3つの質問」で分類すると、こうなります。

* 【質問1】どこを鍵閉める？（保護範囲）
* 【質問2】どんな種類の鍵をかける？（保護手段）
* 【質問3】いつ・どういう考え方で鍵をかける？（設計の思想）

さらに、これを「データベースでやるか」「アプリでやるか」という【管理場所】の視点を加えると、完全に理解できます。

---

## 3つの軸で整理するロック用語

先ほどの3つの質問にあてはめて、各用語を配置したのがこちらの表です。

| 軸 | 用語 | ざっくり解説 |
| --- | --- | --- |
| 【どこを？】| DBロック | データベース全体を閉鎖。メンテナンス用。（範囲：大） |
|  | レコードロック | 特定の1行だけを閉鎖。実務で一番よく使う。（範囲：小） |
| 【どうやって？】 | 共有ロック | 「見るのは自由だけど、書き換えはダメ」という緩め。 |
|  | 排他ロック | 「見るのも書くのも自分以外NG」という固め。 |
| 【いつ・どう考える？】 | 悲観的ロック | 「絶対衝突する！」と疑い、最初から鍵をかけて他者を待たせる。 |
|  | 楽観的ロック | 「まあ衝突しないでしょ」と信じ、DBの鍵は使わず更新直前にバージョン比較する。 |

※ちなみに、悲観的ロックで排他ロックをかけ合ってお互い動けなくなる事故が「デッドロック」です。

---

## DBの枠を超える「アプリケーションロック」

ここで1つだけ浮いている言葉があります。それが「アプリケーションロック」です。

これはDBの中身ではなく、「アプリ（Redisなど）側で二重実行を防ぐ仕組み」のことです。

* DBのロック（レコードロック等）： DBの中にあるテーブルや行を守る
* アプリケーションロック： 「外部決済APIの二重呼び出し」や「バッチ処理の二重起動」など、DBの機能だけでは守れない処理を守る

「誰が管理しているか」というレイヤーが違うだけだと分かれば、もう怖くありません！

---

##  まとめ：会話で混乱したときは「軸」を合わせよう

チームで「ここってロックどうする？」という話になったとき、話が噛み合わない原因の9割は**軸のズレ**です。

* Aさん「ここ悲観的ロックにする？（思想の話）」
* Bさん「うーん、レコードロックでいいんじゃない？（範囲の話）」

こんな会話になっていたら、心の中で「今、思想と範囲の話が混ざってるな」と整理してあげてください。

* どこを？ → レコード単位で
* どうやって？ → 排他ロックをかけて
* いつ？ → 悲観的ロックの思想で事前に守る！

このように組み合わせで語れるようになれば、あなたも立派な「ロックンローラー」です！（違う）

用語の整理ってほんとーーーーーに大事ですね！！！！！！！
